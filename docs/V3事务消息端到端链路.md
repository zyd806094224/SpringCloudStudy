# V3 事务消息端到端链路

> 本文以**一条消息的完整旅程**为主线，把 V3（`createOrderV3`）从发送、半消息、本地事务、回查、消费、幂等、重试到死信兜底的全过程串起来，并标注每一步的代码位置和真实数据变化。
> 分主题的机制讲解（幂等/重试/死信）见 [RocketMQ 使用与商用方案](RocketMQ使用与商用方案.md)；环境搭建见 [RocketMQ 环境接入与商用部署](RocketMQ环境接入与商用部署.md)。

---

## 一、这条链路在解决什么问题

**业务目标**：订单服务创建订单后，要异步通知商品服务扣库存，且保证**最终一致性**——订单成功，库存最终一定要扣；订单失败，库存绝不能扣。

**为什么不用强一致分布式事务（如 Seata）**：跨服务同步事务性能差、锁竞争严重。事务消息用「本地事务 + 消息队列」实现最终一致，性能高、吞吐好，是互联网高并发场景的主流选择。

```
service-order（生产者）                service-product（消费者）
  创建订单 ──半消息/事务消息──►  扣减库存（Redis 幂等）
                  ↑ 失败兜底
          死信队列 → 落库 → 定时重试 → 告警
```

## 二、一条消息的完整旅程（端到端时序）

```
  service-order                                        broker                                        service-product
  ───────────                                  ─────────────────                                  ────────────────

①createOrderV3()
  sendMessageInTransaction
  ("transfer_topic", msg, null)
        │
        │ ② 发送半消息 ──────────────────────►  存储半消息（对消费者不可见）
        │                                       确认 SEND_OK
        │ ③ 半消息成功，立即【同步回调】
        ▼
  executeLocalTransaction(msg, arg)
   · save(order)              ← 本地事务
   · insert(local_message,0)  ← 本地事务
   · return COMMIT/ROLLBACK/UNKNOWN
        │
        ├─ COMMIT  ─────────────────────────►  投递消息（消费者可见）
        ├─ ROLLBACK ────────────────────────►  丢弃半消息
        └─ UNKNOWN  (不发二次确认)            等不到确认 → 触发回查
                                                   │
                ④ broker 主动回查 ◄────────────────┘
                checkLocalTransaction(msg)
                  查 local_message 判状态
                  return COMMIT/ROLLBACK/UNKNOWN
                                                   │
                                          (COMMIT) 投递消息
                                                   │
                                                   ▼ ⑤ 消费
                                          TransferMessageListener.onMessage()
                                            └─ deductStock(txId, productId)
                                                 · Redis SETNX 幂等
                                                 · 扣库存
                                                 ├─ 成功 → ACK（结束）
                                                 └─ 失败 → 抛异常
                                                            │ ⑥ 自动重试（最多3次）
                                                            ▼
                                                       还失败 → 投递死信
                                                            │ ⑦ 死信兜底
                                                            ▼
                                                   TransferDlqListener.onMessage()
                                                     · 落库 dead_letter_message
                                                     · 钉钉告警
                                                            │ ⑧ 定时补偿（每2分钟）
                                                            ▼
                                                   DeadLetterRetryTask
                                                     · 扫 status=0 重试
                                                     · 成功→status=1 / 耗尽→status=2 人工
```

## 三、各阶段代码对照

### 阶段 ① 发送事务消息
**`OrderServiceImpl.createOrderV3()`**（`OrderServiceImpl.java:110-124`）
```java
public boolean createOrderV3() {
    Long productId = 5L;
    String txId = UUID.randomUUID().toString();           // 事务ID（幂等 + 回查依据）
    String msg = String.format("{\"txId\":\"%s\",\"productId\":%s}", txId, productId);
    Message<String> message = MessageBuilder.withPayload(msg).build();
    rocketMQTemplate.sendMessageInTransaction("transfer_topic", message, null);  // 第3参数=arg，传给本地事务
    return true;
}
```
> 关键：消息体里必须带 **txId**（业务唯一标识），它是后续幂等和回查的依据。

### 阶段 ②③ 半消息 + 本地事务回调
半消息发送成功后，`sendMessageInTransaction` **同步**回调 `executeLocalTransaction`：
**`TransferTransactionListener.executeLocalTransaction()`**（`TransferTransactionListener.java:34`）
```java
@Transactional
public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
    // save(订单) + insert(local_message, status=0) 在同一本地事务里
    ...
    localMessageMapper.insert(localMessage);
    return RocketMQLocalTransactionState.COMMIT;   // 成功→投递 / ROLLBACK→丢弃 / UNKNOWN→回查
}
```
> `@RocketMQTransactionListener` 注解让 starter 把这个 listener 注册到 `rocketMQTemplate` 的 producer，所以 `sendMessageInTransaction` 知道回调谁。

### 阶段 ④ 事务回查
仅当 `executeLocalTransaction` 返回 UNKNOWN（或 producer 宕机/超时）时，broker 才会主动回查：
**`TransferTransactionListener.checkLocalTransaction()`**（`TransferTransactionListener.java:75`）
```java
public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
    LocalMessage localMessage = localMessageMapper.selectById(txId);  // 查本地消息表
    ...
    if (status == 1) return COMMIT;   // 本地事务成功 → 投递
    else return UNKNOWN;              // 还不确定 → 继续回查（默认最多15次）
}
```

### 阶段 ⑤ 消费 + 扣库存 + 幂等
**`TransferMessageListener`**（`TransferMessageListener.java:15`）
```java
@RocketMQMessageListener(topic = "transfer_topic",
        consumerGroup = "transfer_consumer_group",
        maxReconsumeTimes = 3)   // 失败3次后进死信
public class TransferMessageListener implements RocketMQListener<String> {
    public void onMessage(String message) {
        ConsumeResult result = transferConsumeService.deductStock(txId, productId);
        if (result == BUSINESS_FAILED) throw new RuntimeException(...);  // 抛异常→触发重试
    }
}
```

**`TransferConsumeServiceImpl.deductStock()`**（`TransferConsumeServiceImpl.java:49`）—— 幂等核心
```java
// 1. SETNX 抢锁（PROCESSING，TTL 24h），失败=已处理过→跳过
Boolean firstTime = redis.setIfAbsent("consume:transfer:" + txId, "PROCESSING", 24, HOURS);
if (!firstTime) return ALREADY_PROCESSED;

// 2. 扣库存
if (product.stock > 0) { product.stock--; update; redis.set(key, "SUCCESS"); return SUCCESS; }
else { redis.delete(key); return BUSINESS_FAILED; }   // 失败释放锁，让重试可重新处理
```

### 阶段 ⑥⑦ 失败重试 → 死信兜底
重试 3 次仍失败 → 投递到 `%DLQ%transfer_consumer_group`：
**`TransferDlqListener`**（`TransferDlqListener.java:26`）
```java
@RocketMQMessageListener(topic = "%DLQ%transfer_consumer_group",
        consumerGroup = "transfer_dlq_consumer_group")
public void onMessage(String message) {
    deadLetterMessageMapper.insert(entity);   // 落库 status=0
    alarmService.sendText("死信消息落库...");   // 钉钉告警
    // 注意：内部 try-catch 不抛异常，避免 DLQ 无限重试
}
```

### 阶段 ⑧ 定时补偿重试
**`DeadLetterRetryTask`**（`DeadLetterRetryTask.java:51`）
```java
@Scheduled(fixedDelay = 120_000L)   // 每2分钟扫一次 status=0 的死信
public void retryDeadLetterMessages() {
    // 复用 deductStock 重试扣库存
    // 成功 → status=1（销账）
    // 业务失败/异常 → retryCount+1，达 MAX_RETRY(5) → status=2（人工）+ 告警
}
```

## 四、实测数据印证（真实跑出来的）

把 `product(id=5)` 库存清零后调 3 次 `createOrderV3`，各存储的实际数据：

| 存储 | 实测数据 | 说明 |
|------|---------|------|
| `local_message` 表 | 4 条，status=**1** | 本地事务记录，全部"已发送" |
| `transfer_topic` | 4 条消息（已消费） | 半消息最终都 COMMIT 投递了 |
| `%RETRY%transfer_consumer_group` | 9 条重试 | 扣库存失败触发的重试 |
| `%DLQ%transfer_consumer_group` | 3 条死信（已被 DLQ 监听器消费） | 重试耗尽进死信 |
| `dead_letter_message` 表 | **3 条**，status=0，retry_count=4 | 死信落库，定时任务已重试4次 |
| Redis | `consume:transfer:{txId}` | 幂等标记（失败时已删除） |

> 这套数据完整印证了「发送→本地事务→回查→消费→幂等→重试→死信→落库→定时重试」全链路。死信在 `dead_letter_message` 表里，**不在 dashboard 面板上**（已被 DLQ 监听器消费掉）。

## 五、商用项目也是这样吗？（重点）

### 结论：机制完全一致，这就是标准答案

**RocketMQ 事务消息的「半消息 + 本地事务 + 回查」是官方推荐、商用通用的范式**。商用项目用 RocketMQ 做最终一致性，核心机制就是你这套，没有别的玩法。所以你这套**机制层面是生产级的**。

### 但工程实现和基础设施有差异

| 维度 | 本项目（学习版） | 商用生产 |
|------|---------------|---------|
| **事务状态记录** | `local_message` 表，status 简单 0/1 | 严谨的事务状态机（INIT/COMMIT/ROLLBACK）+ 独立事务日志表，回查更可靠 |
| **幂等** | Redis SETNX 单点 | Redis + DB 双保险（Redis 宕机也不丢幂等状态）；资金类用 DB 唯一索引 |
| **回查可靠性** | 单实例回查 | 多实例时回查需注意并发（你的回查里"先 update 再判旧值"的写法在商用要避免） |
| **死信处理** | 落库 + 定时重试 + 钉钉告警 | + 监控大盘 + 值班运维流程 + **T+1 全量对账**（终极兜底） |
| **部署** | 单机 docker-compose | NameServer 集群 + Broker 主从/DLedger 高可用 |
| **配置** | 硬编码 topic/group | Nacos 配置中心化 + ACL 鉴权 + namespace 隔离 |
| **监控** | 靠日志 | Prometheus + Grafana + rocketmq-exporter，消费延迟/积压/失败率告警 |
| **幂等 key** | txId（UUID） | 同（业务唯一ID，商用也这么选） |

### 事务消息的价值定位
事务消息解决的是 **"本地事务成功 → 消息一定可靠发出去"**（消息投递可靠性），**不是**"业务能不能做"。它适合下游操作**必然成功、或失败可补偿、不阻塞主流程**的场景——比如支付成功后加积分、下单后发通知、DB 变更后同步 ES。

> ⚠️ 像下单扣库存这种**资源有限、必须即时确认**的场景，商用主流是**同步扣减 / 预扣**，不该用事务消息异步扣（否则会出现"下单成功但没库存"）。详见下一节「事务消息该不该用」。

### 你这套离生产还差什么（如果真要上）
1. `executeLocalTransaction` 里别 `catch` 吞异常（会导致 `@Transactional` 不回滚，事务语义被破坏）
2. `checkLocalTransaction` 改成「先查再判，根据查询结果决定」，不要先 update 再用旧对象判断
3. 幂等关键场景加 DB 唯一索引兜底
4. 死信接监控告警大盘 + 加 T+1 对账
5. 部署换高可用集群（见 [环境接入与商用部署](RocketMQ环境接入与商用部署.md) 第五节）

## 六、事务消息该不该用——场景选型（重要）

> 很多人把事务消息当成"最终一致性的银弹"，什么跨服务场景都想套——这是误解。**选错场景会踩大坑**（比如下单扣库存用事务消息，用户已经看到"下单成功"，结果库存压根没有）。

### 先分清两件事
| 问题 | 归属 | 该用什么 |
|------|------|---------|
| **业务能不能做**（库存够不够、余额够不够） | 业务层，必须即时确认 | 同步扣减 / 预扣 |
| **该发的消息有没有发出去** | MQ 层，保证可靠投递 | 事务消息 |

### ✅ 适合事务消息（下游必然成功 / 可补偿）
- 支付成功 → 加积分、发券
- 下单成功 → 发短信 / APP 推送
- 支付成功 → 通知物流发货
- DB 数据变更 → 同步到 ES / 缓存
- 用户注册 → 发欢迎邮件

共同点：**下游失败不影响主业务正确性，重试或补偿能兜住**。

### ❌ 不该用事务消息（资源有限、需即时答复用户）
- 下单扣库存
- 扣余额 / 扣款
- 抢名额、抢席位

这些必须在**用户操作的当下**给出准确结果，不能"先成功后异步确认"。

### 下单扣库存，商用主流怎么做（同步扣减）
```sql
-- 乐观扣减：影响行数 >0 表示库存够，=0 表示售罄
UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0
```
- 行数 > 0 → 库存够，下单成功
- 行数 = 0 → 直接告诉用户"售罄 / 库存不足"

更精细的成熟电商用**预扣 + 超时释放**：下单锁定库存（stock-1, locked+1），给 15 分钟支付窗口，支付成功转真扣、超时未支付释放锁定。

> 这两种都是**同步确认库存**，根本用不上事务消息。

### 本项目 V3 用"扣库存"演示，是错的吗？
不是错，是**教学选择**——扣库存是个大家都看得懂的业务，适合演示事务消息的半消息 + 回查 + 幂等 + 死信机制。但它**不是**真实"下单扣库存"的最佳方案。心里要分清"学事务消息机制"和"学库存方案"两件事。

### 万一真用了异步扣库存（少数场景），"下单成功但没库存"怎么兜
1. 死信 + 告警 + 人工补偿（就是本项目 V3 的死信兜底）
2. Saga 补偿事务：扣失败 → 自动发反向消息取消订单 + 退款
3. T+1 对账：扫"订单成功但库存没扣"的不一致数据，主动补偿

但这些都是**事后擦屁股**，体验远不如"下单时直接告诉售罄"。

### 一句话选型框架
> **资源有限、必须即时给用户准确答复（库存 / 余额 / 席位）→ 同步扣减 / 预扣，别用事务消息。**
> **下游必然成功或失败可补偿、不阻塞主流程（积分 / 通知 / 索引同步 / 发货）→ 用事务消息，保证消息可靠投递。**

## 七、关键设计要点 & 易错点（实测踩过的）

### ✅ 设计要点
1. **txId 必须是业务唯一标识**：贯穿本地事务表、幂等 key、回查，是整条链路的"主键"
2. **本地事务和消息记录同库同事务**：保证「业务成功 + 消息记录成功」原子性
3. **幂等三态**：PROCESSING（处理中）/ SUCCESS（成功）/ 删除（失败可重试）
4. **DLQ 监听器内部不抛异常**：避免死信队列内部无限重试死循环
5. **死信定时重试复用消费逻辑**：保证幂等策略一致

### ⚠️ 易错点（本项目里的真实坑）
| 坑 | 现象 | 根因 | 正确做法 |
|----|------|------|---------|
| `@Transactional` 里 catch 不抛 | 1/0 异常但事务没回滚，订单和消息都存了 | catch 吞了异常，Spring 感知不到，不回滚 | catch 后若要回滚，手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` 或重新抛出 |
| 回查先 update 再判旧值 | 回查永远返回 UNKNOWN（第一次） | `localMessage.getStatus()` 拿的是查询快照，不是 update 后的值 | 先 `selectById` 拿最新状态判断，再决定是否 update |
| dashboard 看不到死信 | 以为死信没产生 | 死信已被 DLQ 监听器消费落库 | 查 `dead_letter_message` 表，不是面板 |
| 发消息连不上 broker | `connect to x.x.x.x:10911 failed` | brokerIP1 不是当前宿主机 IP | 改 broker.conf 的 brokerIP1，重启 broker |
